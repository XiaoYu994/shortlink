# Project Service 重构需求规格书

## 1. 项目背景

### 1.1 当前状态
- **模块名称**: `shortlink-project-service`
- **核心功能**: 短链接创建、跳转、统计、风控、冷热数据分离
- **技术栈**: Spring Boot 3.2.5 + MyBatis-Plus + Redis + RocketMQ + ShardingSphere
- **主要问题**:
  - `ShortLinkServiceImpl` 代码量达 675 行，职责不清晰
  - Redis Stream 和 RocketMQ 双实现并存，维护成本高
  - 冷热数据分离逻辑分散在多处，缺乏统一管理

### 1.2 重构驱动因素
- **主要驱动**: 功能扩展困难
- **次要驱动**: 代码可维护性差、技术债务积累

## 2. 重构目标

### 2.1 核心目标
1. **代码结构优化**: 将臃肿的 Service 层按职责拆分成多个子服务
2. **性能优化**: 优化缓存策略、数据库查询、并发处理
3. **代码质量提升**: 消除代码坏味道、提高可读性、减少重复代码
4. **技术债务清理**: 移除过时代码、统一技术方案、修复已知问题

### 2.2 约束条件
- **向后兼容**: 必须保持 API 接口、数据库结构的向后兼容
- **零停机**: 重构过程不影响现有功能运行
- **渐进式**: 采用渐进式重构，每个阶段可独立交付

## 3. 重构范围

### 落地说明（2026-08-18）

P0 / P1 已按当前主线落地，类名与最初草案略有收敛：

- 创建 / 修改 / 查询：`ShortLinkCreateService` / `ShortLinkUpdateService` / `ShortLinkQueryService`，由 `ShortLinkCoreService` 组合实现
- 缓存：`ShortLinkCacheService`，实现为 `ShortLinkCacheHelper`
- 冷热数据：`ShortLinkColdDataService`（迁移、回温、归并查询）
- 门面：`ShortLinkService` / `ShortLinkServiceImpl`，Controller 只依赖门面
- MQ 已统一 RocketMQ；Redis Stream 已移除
- 缓存 TTL 增加抖动；跳转记录命中率；分页记录查询耗时；冷迁移失败有指标与告警
- 批量创建上限 100；用户级限流（网关 + user/project 拦截器）
- 短链展示协议可配置 `short-link.domain.protocol`

未按原文做的验收项：80% 覆盖率、SonarQube、正式 1000 QPS 压测报告、OpenAPI。这些不影响当前单机部署可用性。

### 3.1 优先级 P0（必须完成）

#### 3.1.1 Service 层拆分
**当前问题**:
- `ShortLinkServiceImpl` 包含 675 行代码
- 混合了创建、更新、查询、缓存、统计等多种职责
- 违反单一职责原则，难以测试和维护

**重构方案**:
将 `ShortLinkServiceImpl` 拆分为以下子服务：

1. **ShortLinkCreateService** - 短链接创建
   - 短链接生成（布隆过滤器/分布式锁）
   - 数据库插入（热库 + 路由表）
   - 缓存预热
   - 布隆过滤器维护

2. **ShortLinkUpdateService** - 短链接修改
   - 同分组修改
   - 跨分组修改（读写锁）
   - 缓存失效

3. **ShortLinkQueryService** - 短链接查询
   - 分页查询（热库+冷库合并）
   - Redis 排行榜查询
   - 分组统计查询
   - 今日统计填充

4. **ShortLinkCacheService** - 缓存管理
   - 多级缓存读取（本地缓存 → Redis → 数据库）
   - 缓存预热
   - 缓存失效
   - 空值缓存处理

5. **ShortLinkColdDataService** - 冷热数据管理
   - 冷数据迁移
   - 热数据回温
   - 冷热数据合并查询

**保留原接口**:
- `ShortLinkService` 接口保持不变，作为门面（Facade）
- `ShortLinkServiceImpl` 重构为门面实现，委托给各子服务

#### 3.1.2 消息队列统一
**当前问题**:
- 同时存在 Redis Stream 和 RocketMQ 两套实现
- 通过配置切换，但代码重复度高
- 维护成本高，容易出现不一致

**重构方案**:
1. **统一使用 RocketMQ**
   - 移除所有 Redis Stream 相关代码
   - 保留 `AbstractCommonSendProduceTemplate` 抽象模板
   - 统一消息发送、消费、重试、幂等处理

2. **保留的生产者**:
   - `ShortLinkCacheProducer` - 缓存失效消息
   - `ShortLinkRiskProducer` - 风控审核消息
   - `ShortLinkExpireArchiveProducer` - 过期归档消息

3. **保留的消费者**:
   - `ShortLinkCacheConsumer` - 缓存失效处理
   - `ShortLinkRiskConsumer` - 风控审核处理
   - `ShortLinkExpireArchiveConsumer` - 过期归档处理

4. **移除的代码**:
   - 所有 `*RedisProducer` 和 `*RedisConsumer`
   - Redis Stream 配置类
   - Redis Stream 相关依赖

### 3.2 优先级 P1（重要但非紧急）

#### 3.2.1 冷热数据分离优化
**当前问题**:
- 冷热数据查询逻辑分散在 `ShortLinkServiceImpl` 中
- 合并查询性能不佳（内存排序）
- 缺乏统一的冷热数据管理策略

**重构方案**:
1. 创建 `ShortLinkColdDataService` 统一管理
2. 优化冷热数据合并查询算法（归并排序）
3. 添加冷热数据迁移监控和告警
4. 优化回温机制（阈值可配置）

#### 3.2.2 缓存策略优化
**当前问题**:
- 多级缓存逻辑分散
- 缓存失效策略不统一
- 缺乏缓存监控

**重构方案**:
1. 创建 `ShortLinkCacheService` 统一管理
2. 实现缓存穿透、击穿、雪崩防护
3. 添加缓存命中率监控
4. 优化缓存 TTL 策略

#### 3.2.3 查询性能优化
**当前问题**:
- Redis 排行榜查询与数据库查询混合逻辑复杂
- 冷热数据合并查询性能不佳
- 缺乏查询降级机制

**重构方案**:
1. 优化 Redis 排行榜查询逻辑
2. 实现查询降级机制（Redis 失败降级到数据库）
3. 添加查询性能监控
4. 优化分页查询算法

### 3.3 优先级 P2（可选优化）

#### 3.3.1 代码质量提升
- 添加单元测试（目标覆盖率 80%）
- 添加集成测试
- 代码规范检查（Checkstyle + Spotless）
- 添加详细的 JavaDoc 注释

#### 3.3.2 监控和告警
- 添加业务指标监控（创建成功率、查询耗时等）
- 添加缓存命中率监控
- 添加消息队列消费延迟监控
- 添加冷热数据迁移监控

## 4. 功能需求

### 4.1 短链接创建
- **输入**: 原始 URL、分组 ID、有效期、描述
- **输出**: 短链接 URL、分组 ID、原始 URL
- **业务规则**:
  - 支持布隆过滤器和分布式锁两种去重策略
  - 自动进行缓存预热
  - 自动加入布隆过滤器
  - 异步触发风控审核
  - 异步抓取网站图标
- **性能要求**:
  - 单次创建响应时间 < 200ms
  - 支持批量创建（最多 100 条）

### 4.2 短链接修改
- **输入**: 短链接 URL、新的原始 URL、新的分组 ID、有效期、描述
- **输出**: 无
- **业务规则**:
  - 同分组修改：直接更新
  - 跨分组修改：使用读写锁，先删除后插入
  - 自动清除缓存
  - 更新路由表
- **性能要求**: 响应时间 < 300ms

### 4.3 短链接查询
- **输入**: 分组 ID、页码、每页大小、排序字段
- **输出**: 分页数据（短链接列表、总数）
- **业务规则**:
  - 支持按创建时间、总 PV/UV/UIP、今日 PV/UV/UIP 排序
  - 今日排序优先从 Redis 排行榜查询
  - 热库+冷库合并展示
  - 自动填充今日统计数据
- **性能要求**:
  - 响应时间 < 500ms
  - 支持大数据量分页（百万级）

### 4.4 短链接跳转
- **输入**: 短链接 URI
- **输出**: 重定向到原始 URL
- **业务规则**:
  - 多级缓存查询（本地缓存 → Redis → 数据库）
  - 检查有效期和启用状态
  - 异步记录访问统计
  - 支持冷数据自动回温
- **性能要求**:
  - 响应时间 < 50ms（缓存命中）
  - 响应时间 < 200ms（数据库查询）

### 4.5 冷热数据管理
- **输入**: 无（定时任务触发）
- **输出**: 迁移日志
- **业务规则**:
  - 每天凌晨 2:30 执行冷数据迁移
  - 90 天未访问的链接迁移到冷库
  - 冷链接访问量超过 1000 次自动回温
  - 过期链接有 30 天宽限期
- **性能要求**:
  - 批量迁移（每批 200 条）
  - 不影响正常业务

## 5. 非功能需求

### 5.1 性能要求
- **并发**: 支持 1000 QPS
- **响应时间**:
  - 创建: < 200ms
  - 查询: < 500ms
  - 跳转: < 50ms（缓存命中）
- **可用性**: 99.9%

### 5.2 可维护性要求
- **代码规范**: 遵循阿里巴巴 Java 开发手册
- **测试覆盖率**: 核心业务逻辑 > 80%
- **文档**: 完整的 JavaDoc 和架构文档

### 5.3 可扩展性要求
- **水平扩展**: 支持多实例部署
- **功能扩展**: 易于添加新的统计维度、新的缓存策略

### 5.4 安全性要求
- **URL 白名单**: 支持配置跳转域名白名单
- **风控审核**: 自动检测恶意 URL
- **限流**: 支持用户级别限流

## 6. 技术约束

### 6.1 必须遵守
- **Java 版本**: Java 17
- **Spring Boot 版本**: 3.2.5
- **数据库**: MySQL 8.x + ShardingSphere 5.5.0
- **缓存**: Redis + Caffeine
- **消息队列**: RocketMQ（统一使用）
- **代码规范**: 阿里巴巴 Java 开发手册

### 6.2 禁止使用
- **Redis Stream**: 统一使用 RocketMQ
- **硬编码**: 所有配置项必须外部化
- **魔法值**: 使用常量或枚举

## 8. 风险评估

### 8.1 技术风险
| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| Service 拆分导致性能下降 | 高 | 低 | 性能测试验证，必要时合并部分服务 |
| 消息队列切换导致消息丢失 | 高 | 中 | 灰度发布，双写验证 |
| 冷热数据合并查询性能问题 | 中 | 中 | 优化算法，添加缓存 |
| 缓存一致性问题 | 高 | 低 | 完善缓存失效机制，添加监控 |

### 8.2 业务风险
| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 重构期间功能不可用 | 高 | 低 | 渐进式重构，每个阶段独立交付 |
| API 不兼容导致前端报错 | 高 | 低 | 严格保持 API 兼容，充分测试 |

## 10. 附录

### 10.1 术语表
- **热数据**: 90 天内有访问的短链接数据
- **冷数据**: 90 天未访问的短链接数据
- **回温**: 冷数据访问量超过阈值后迁移回热库
- **布隆过滤器**: 用于短链接去重的概率数据结构
- **分布式锁**: 用于短链接去重的强一致性方案
